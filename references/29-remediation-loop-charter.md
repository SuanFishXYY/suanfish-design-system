# 📜 ref 29 · 整改闭环追踪制 v1.0.0

> *ref 28 的 G6 退回带缺陷清单——清单给了，然后呢？没这套制度，缺陷清单就是一张废纸，退回等于白退。*
> *本制度把「退回 → 销项」写成五步闭环：开单 → 认领 → 修复 → 复审 → 销项。不闭环就是踩红线一。*

## 版本同步契约

| 字段 | 说明 |
| --- | --- |
| `charter_version` | 本制度的 semver |
| `bound_to_ruleset_version` | 对应 ref 15/16/19 三份规则集的 `ruleset_version`（取三者最高） |

**R1 开单 / R4 复审时检查同步**。如果 `bound_to_ruleset_version` 落后于规则集当前版本，工单的 `acceptance` 销项标准可能已失效（旧规则被废 / 新规则加入）→ 输出 `CHARTER_OUT_OF_SYNC`，强制 owner 同步本制度后重开工单。同 ref 28 契约。

## 0. 制度一句话

> **G6 退回即生成缺陷工单 → owner 限时认领 → 逐项修复 → 复审只验缺陷项 → 全销才重开 case。SLA 超时自动升级，屡犯同缺陷强制提规则 PR。退回不带追踪 = 3.25。**

## 1. 与 ref 28 的对接点

```
ref 28 六步流水线                      ref 29 整改闭环
─────────────────────                ─────────────────────
G1 立案 ─ G2 辩论 ─ G3 评分            (生成物首次过门)
        ↓ FAIL
G4 投票 ✗ / G5 蓝军否决                ┌─ R1 开单 (缺陷清单→工单)
        ↓                              │  R2 认领 (owner + SLA)
G6 退回 ──────────────────────────────→│  R3 修复 (逐项销项)
                                       │  R4 复审 (只验缺陷项)
                                       │  R5 销项 (全销→case 重开)
                                       └───────┐
                                        ↓ 全销  │ 未销 → §5 升级
                                       重开 case ─→ 回 ref 28 G1 复审
```

- **入口**：① ref 28 G6 判定 `FAIL` 的瞬间，自动触发本制度 R1；② ref 30 K3 判定「衰弱」时，复用本制度 R1 开 W 级工单限改（事后门内容衰弱回灌退回门，见 ref 30 §2-K3 / review-orchestrator 跨门流转）。两入口共用同一套 R1-R5 + SLA。
- **出口**：R5 全销项 → `case_id` 重开，回 ref 28 **从 G3 复审起**（不重跑 G1 立案/G2 辩论，除非 BRIEF 本身变了）。
- **同一 `case_id` 全程复用**：整改记录挂在原 case 目录下（见 ref 28 §6），不另起 case。

## 2. 五步闭环

### R1 · 开单
- **触发**：ref 28 G6 输出 `FAIL` + `06_verdict.md` 缺陷清单。
- **动作**：ui-auditor 把每条缺陷拆成独立工单，写入 `case_id/remediation/ticket-{N}.md`：
  ```
  ticket-{N}:
    defect_id: D-{case_id}-{N}
    source: G3 评分维 / G4 投票理由 / G5 蓝军否决定位
    rule_hit: (如适用) R-xx / W-xx / H-xx
    owner_agent: (该维主审 / 该规则 owner)
    severity: P0 致命 / P1 阻断 / P2 警告
    acceptance: 可证伪的销项标准（grep 什么、验什么）
    sla: 按 §3 表
    status: OPEN
  ```
- **销项标准必须可证伪**——「改好」不算标准，「`grep onbEureka` 返回空」才算。不可证伪的工单 = 3.25，等于无法验收。
- P0 致命缺陷（R 规则命中 / 蓝军否决）→ **工单生成即抄送 sage_congress**，进入升级预备态。

### R2 · 认领
- **机制**：owner agent 抢认领（先到先得），认领即 SLA 计时开始。
- **法定认领人**：工单 `owner_agent` 字段指定的 agent；若该 agent 缺席，由同 tier 同类替补。
- **无人认领 SLA**：S 级工单 2h 内无人认领 → 自动指派 + 对原 owner 记一次「弃单」。
- **认领产出**：`ticket-{N}.md` 写入 `claimed_by` + `claimed_at` + `eta`。

### R3 · 修复
- owner 按 `acceptance` 标准逐项修复，**禁止超出工单范围改别的**（防夹带私货——改 A 破坏 B 是 L2）。
- 每条缺陷修复后，owner 在工单写明「怎么改的 + 证据」（grep 输出 / 截图 / 测试结果）。
- **禁止空口销项**：写「已修复」没贴证据 = 踩 ref 28 红线一，工单退回 R3。

### R4 · 复审
- **只验缺陷项，不重审整件**（省 token，同 v4.2「简单事 2 个圣人就够」精神）。
- 复审员 = 该工单 `source` 对应的原审 agent（G3 主审 / G5 蓝军），保证标准一致。
- 复审三态：
  - ✅ **PASS**：缺陷销项，工单 `status → CLOSED`
  - ❌ **FAIL**：未达 `acceptance`，工单退回 R3，记一次「返工」
  - ⚠️ **DRIFT**：缺陷销了但引入新缺陷（改 A 破坏 B）→ 新缺陷开新工单 + 原工单延后销项
- 复审必须贴**可证伪判定**（哪条 acceptance 没过 / 哪条过了），否则复审无效（防复审放水）。

### R5 · 销项 / 升级
- **全销项**（该 case 所有 OPEN 工单 CLOSED）→ `case_id` 重开，回 ref 28 G3 复审。
- **部分销项**→ 继续走未销工单；剩余工单触发 §5 升级条件则升级。
- **销项归档**：所有工单 CLOSED 后，`case_id/remediation/` 打包进 `06_verdict.md` 附录，可追溯。

## 3. SLA 严重度矩阵

| severity | S 级 case | A 级 case | B 级 case | 超时后果 |
| --- | --- | --- | --- | --- |
| **P0 致命** | 24h | 48h | 不适用（B级无P0） | 自动升级 §5 |
| **P1 阻断** | 72h | 5d | 不适用 | 升级 §5 |
| **P2 警告** | 5d | 10d | 14d | 警告 + 计入指标 |

- SLA 计时单位：工单认领（R2）→ 销项（R5 CLOSED）。
- **法定节假日 / 等 owner 同步规则集的时间不计入 SLA**（公平性，防甩锅给外部阻塞）。

## 4. 整改质量回扣（防敷衍整改）

> 整改不是「改了就行」，改得烂要回扣。防止「凑合改改蒙混过 R4」。

| 信号 | 判定 | 回扣 |
| --- | --- | --- |
| 同一工单 R3→R4 FAIL ≥ 2 次 | 敷衍整改 | owner 记「返工²」，case 升级一档 |
| 修复夹带未授权改动（DRIFT） | 改 A 破坏 B | 新开工单 + 原工单 SLA 重置 |
| 空口销项（无证据） | 踩红线一 | 工单退回 + owner 记「虚假完成」 |
| 销项后 30 天内同位置再发同缺陷 | 屡犯 | 触发 §6 提规则 PR |

## 5. 超时升级链

SLA 超时不是「等等就好」——**P0/P1 超时自动升级**（防缺陷工单变无主僵尸）；**P2 警告级超时止于「警告 + 计入指标」**（§3 矩阵），不进升级链：

```
SLA 超时
  ↓
L1 换人   工单重派给同 tier 替补 + 原 owner 记弃单
  ↓ 再超时
L2 提级   case 升级一档 (B→A→S) + 抄送 sage_congress
  ↓ 再超时
L3 仲裁   sage_congress 仲裁: 重做 / 降级放行 / 废弃 case
  ↓ 再超时
L4 冻结   case 冻结, 进「僵尸工单」看板, 季度清理
```

- **L3 仲裁的「降级放行」是红线动作**——必须 sage_congress 集体 2/3 通过 + 蓝军无否决，且在 `06_verdict.md` 标注「带病放行」+ 缺陷转 [ref 30 K1](30-posthoc-governance-charter.md) 归档复审跟踪。不得偷偷降级。
- **L4 冻结 ≠ 删除**——僵尸工单进看板，季度由 owner 复盘：是真无主还是制度本身卡住了？

## 6. 屡犯 → 提规则 PR（个案沉淀为制度）

> ref 28 §8 的复盘机制在整改侧的落地：同一类缺陷反复出现，就别再靠人盯，让规则集吃下它。

**触发条件**（任一）：
- 同一 owner 在 30 天内被开 ≥ 3 张同 `rule_hit` 的工单。
- 同一缺陷位置在销项后 30 天内复发。
- 同一 `acceptance` 标准在 R4 被判 FAIL ≥ 3 次（说明标准本身有问题）。
- **🔴 M 轨反哺（v4.2.7 哲理审计 R8）**：ref 30 M3 元审发现"某圣人持续失准"（同一圣人 M2 校准警告 ≥ 2 次/季度，见 ref 30 §M5）→ 说明该圣人反复踩的失准模式**未被现有 R 规则覆盖**，触发 §6 提规则 PR。理由：M 轨发现的是"审核者级"制度缺口（规则没拦住他的失准），与前三条"工单级"缺口同源——都该沉淀为规则，不该只反哺 K1 重采样就完。补此触发条件闭合 M 轨→学习闭环的断链。

**动作**：
1. ui-auditor 起草**新规则 PR** 进 ref 15/16/19（按归属 owner），把这类缺陷从「人工审」变成「规则 grep」。
2. PR 合并后，该类缺陷进 R 规则集 → 以后 G5 蓝军自动拦，不用再走整改闭环。
3. 记入 `case_id` 的 `规则沉淀` 字段，可追溯。
4. **🔴 版本同步（v4.2.7 哲理审计 R8 · 补规则 PR 合并后版本主缺位）**：PR 合并是规则集变更的**主动源头**，必须由提 PR 的 owner 同步升版本，否则 charter-lint B1b/B2b 会抓到漂移：① 升 `ruleset_version`（ref 15/16/19 的 semver，新增 R 规则 = minor bump）；② 同步 `bound_to_token_version`（ref 15/16，若新规则涉及令牌维度）；③ 同步 ref 28/29/30 的 `bound_to_ruleset_version` = 升后的 ruleset_version（取三者最高）；④ 跑 `charter-lint` 验证零漂移。漏同步 = 规则进了库但版本号没动 = 制度与规则集脱节 = 该 PR 不算合并完成。

> **一个问题进来，一类问题出去。** 修完不沉淀规则，下次同样的坑再炸，你就准备开第三张一样的工单。

```
case_id/
├── ... (ref 28 的 01-06)
└── remediation/
    ├── ticket-1.md        ← 每条缺陷一工单 (defect_id/owner/SLA/acceptance/状态)
    ├── ticket-2.md
    ├── ...
    ├── remediation-log.md ← 整改时间线 (开单/认领/修复/复审/销项 全留痕)
    └── escalation.md      ← 升级记录 (如有)
```

> **没有 remediation-log.md 的「已整改」= 踩红线一。** 退回追踪没留痕 = 整改未闭环。

## 8. 边界 case 与冲突裁决

| 情形 | 裁决 |
| --- | --- |
| owner 认为缺陷清单本身错了 | 不许擅自关工单。提「缺陷异议」→ 原审 agent 复核，异议成立则工单作废，不成立则 SLA 照计。 |
| 复审员 = 原审 agent，怕自己打脸放水 | P0 工单复审强制换人（另一蓝军交叉复审）；P1/P2 允许原审复审但抽检 10%。 |
| 修复需要改 BRIEF 本身 | 停整改，回 ref 28 G1 重新立案（BRIEF 变了 = 案子变了）。 |
| 多工单互相依赖 | 标 `blocked_by`，按依赖序销项；被阻塞工单 SLA 暂停。 |
| case 已被 L4 冻结，后来发现其实是 P0 | 解冻 + 升级回 L1 重派，不计原 SLA 超时账。 |
| 整改期间规则集版本升级 | 以**最新规则集**为准复审；若新规则导致已销项工单复现，开新工单不算返工。 |

## 9. 制度自检指标（季度 · ui-auditor 出 dashboard）

| 指标 | 健康区间 | 异常信号 |
| --- | --- | --- |
| 工单平均销项周期 | < SLA 的 50% | 持续接近 SLA = 整改吃力 |
| R3→R4 返工率 | < 20% | > 30% = 敷衍整改 or acceptance 不清 |
| 空口销项率 | = 0 | > 0 = 红线一被踩，红色警报 |
| DRIFT 率（改A破坏B） | < 5% | > 10% = 缺乏回归测试 |
| 屡犯触发提规则 PR 数 | > 0 | 长期 0 = §6 机制没运转，缺陷在原地打转 |
| 僵尸工单（L4）数 | 趋近 0 | 堆积 = 制度卡点，需修制度本身 |
| 降级放行数 | 偶发 | 频繁 = 上游需求/评审标准有问题 |

> 这些指标本身就是 §10 季度自检的输入——制度审制度，闭环套闭环。

## 10. 制度自检（owner 季度执行）

每季度由 ui-auditor + sage_congress owner 联合跑一次：

- [ ] §9 指标 dashboard 是否采集齐全？有无长期红区？
- [ ] 僵尸工单是否清理？根因是人的问题还是制度卡点？
- [ ] 屡犯触发的规则 PR 是否都合并了？合并后该类工单是否真的消失了（验证规则生效）？
- [ ] 降级放行的 case 事后是否被 [ref 30 K 轨归档复审](30-posthoc-governance-charter.md)（K1 重采样）跟踪到？
- [ ] 复审交叉机制（P0 换人）是否被绕过？

> 不审审核者，审核就腐烂——本制度的复审员本身也要被抽检。这一条由 [ref 30 M 轨元审计](30-posthoc-governance-charter.md)收口：M3 元审抽检复审员是否放水、M5 失准下岗。降级放行的「带病内容」由 ref 30 K1 强制重采样跟踪。
